# Interview Answers (max 200 words each)

## 1. How would you structure design tokens? 
ANS. Using my project 'Liz's Grillz Bookings' as reference, I structure tokens in two layers. The first is the palette: raw tonal values generated from my brand color. I sampled the orange ring of the Liz’s Grillz logo (
#D75C19), found that white text on it measured about 3.9:1, and darkened it to 
#C2410C, which measures about 5.2:1. I pinned that as primary 40 so the palette generated around it instead of drifting away from the brand. The second layer is color roles: names for jobs, such as primary, on-primary, surface and on-surface. Roles point at the palette, and the interface uses only roles, never palette values or hex codes. The Figma variables export to JSON, and a script converts that to CSS variables, so Figma stays the single source of truth. I tested this on a branch: changing the brand color at the source recolored everything that referenced a role, but the one element I hardcoded stayed orange.

## 2. When is a token change breaking?
ANS. A token change is breaking when something that depends on it stops working or stops meaning what it did. In my project the tokens end up as CSS variables, so the most dangerous breaks are silent: if I rename or delete --color-primary, nothing fails to build, the browser just drops the style and the button falls back to a default. Changing what a role means is also breaking, for example making on-primary dark when buttons assume white text. So is changing a value in a way that breaks a guarantee: my primary is 
#C2410C at about [5.2:1] with white, and a lighter orange would pass visually but fail the 4.5:1 standard. A plain value change that every consumer still handles is not breaking, it’s the point of tokens. I saw this on a branch: changing the brand colour recoloured everything that used a role, but the tagline I had hardcoded stayed orange.

## 3. How would you support multiple brands and themes?
ANS- I’d keep three layers: primitives (the raw palette), roles (primary, on-primary, surface, on-surface) and components, which use roles only. A theme such as dark mode keeps the same primitives and points the roles at different tones, so primary uses a lighter tone on a dark surface. A new brand swaps the primitives: a new source colour generates a new palette, and the roles keep the same names so no component changes. In CSS, I’d redefine the role variables under a scope like [data-theme="dark"] or [data-brand="x"]. I’ve only built one brand, but the experiment showed the mechanism: when I changed the source colour on a branch, everything using a role followed it, and only the hardcoded tagline didn’t. The cost is that every theme needs its contrast pairs re-measured. My primary is about [5.2:1] with white, and a dark theme might fail that.I have not tested dark mode yet but would be open to test it. 
 

## 4. Can tokens guarantee accessible contrast?
ANS- No. A token is just a named value, and on-primary has no idea what background it will sit on, so changing the primary value can break contrast without any error. What tokens can do is make the pairing explicit: my roles come in pairs, such as primary with on-primary, and I measured each pair when I defined it. My logo orange (
#D75C19) gave about [3.9:1] against white, below the 4.5:1 AA standard for normal text, so I darkened it to 
#C2410C at about [5.2:1]. That check happened at the source, once, instead of relying on each developer to remember it. It doesn’t stay guaranteed, though. If someone edits a palette value, the pair can fail again, so contrast has to be re-measured on every change, ideally by an automated check in the build. 

## 5. How do you ensure that colour contrast guidelines are met within a website or application's design?
ANS- I check contrast at three points. First, when I define roles: for every pair I plan to use, such as primary with on-primary, I measure the ratio against the WCAG AA thresholds: 4.5:1 for normal text, 3:1 for large text and for non-text elements like input borders and focus rings. In my project, my logo orange (
#D75C19) measured about [3.9:1] with white, so I darkened it to 
#C2410C at about [5.2:1] and recorded each ratio in my colour roles document. Second, when something changes: any edit to a palette value means re-measuring the affected pairs, because the tokens won’t warn me. Third, on the built page, I check the real combinations, including text over images, and hover, focus and disabled states, since those are the ones pair-checking misses. I measured with WCAG ratios, not APCA, which is proposed for WCAG 3 and isn’t the current standard. 

## 6. Can you discuss the differences between WCAG levels A, AA and AAA?
ANS-WCAG has three conformance levels, and each includes the one below it. Level A is the minimum: without it some people can’t use the content at all, for example images without text alternatives, content that can’t be operated by keyboard, or errors shown by colour alone. Level AA is the usual legal and procurement target and adds things like text contrast of 4.5:1 (3:1 for large text), text that resizes, and visible keyboard focus. Level AAA is the strictest, with 7:1 contrast for normal text, but WCAG itself says it isn’t realistic as a blanket requirement because some content can’t meet every AAA criterion, so I’d adopt AAA items selectively. My project targets AA. My primary, 
#C2410C, measures about [5.2:1] with white, which passes AA but fails the 7:1 AAA threshold, and I accepted that because darkening it further would drift from the logo orange.  

## 7. Discuss the importance of semantic HTML in the context of accessibility.
ANS- Semantic HTML means using the element that matches the job, so assistive technology and the browser know what each thing is. A real <button> is announced as a button, is reachable with Tab, and works with Enter and Space. A <div> styled to look like one has none of that until you rebuild it by hand with a role, tabindex and key handlers, and people usually miss something. Headings and landmarks such as <h1>, <nav> and <main> let screen reader users jump through a page instead of hearing all of it. It is necessary but not sufficient: a page with correct elements can still fail on contrast, labels or focus order. On my home page, [I checked that “Liz’s Grillz Bookings” is a real <h1> and “Check a date” is a <button>, with the price shown in a <section>/<article>].

## 8. How do you handle design handoff to developers using Figma?
ANS- My handoff is Figma variables, then a JSON export, then CSS variables. I define colours, type and shadows as variables in Figma, export them with a plugin as JSON, and have an agent convert that to CSS variables. The first export left out my colours until I explicitly included Figma variables, so I now open the JSON and search it for my primary hex (
#C2410C) before using it. Developers use colour roles, never palette values, so a Figma change flows through without edits to components. I also verify what the agent did instead of trusting it. 


## 9. Why do AI-generated interfaces tend to look generic, and what specifically do you hand an agent to stop it?
ANS- Without constraints, an agent produces the most likely interface, which is the average of the sites it has seen, so unrelated projects come out looking the same. To stop that, I give it inputs it can’t guess: my exported tokens JSON, the CSS variables, my type scale and my colour roles, anchored on a brand orange I sampled from the logo. I also give it rules: use roles only, no hardcoded colour, size, font or shadow values, and ask me instead of inventing a token. Handing it over isn’t enough, because an agent can ignore a system it was never given, so I verify. In my project I searched the codebase for raw hex values, and I asked which typography style it used for the heading. 

## 10. Your line height for display large is a specific number. Why that number and not one step either side of it? What would you lose with each?
ANS- My display large style is 64px with a line height of 96px, which is a multiplier of 1.5. One step tighter, 1.4, gives 89.6px. That is a fractional pixel value, and the lines of a wrapped heading sit close enough to read as one block, which would suit a short headline, but with my letter spacing already tight, I’d risk the lines feeling cramped. One step looser, 1.6, gives 102.4px, also fractional, and the lines start to read as separate items, with more wasted vertical space. On a phone that pushes my “Check a date” button further down the screen. I chose 1.5 because it is a whole number (96 is a multiple of 8, so it sits on a spacing grid) and it keeps wrapped lines related without crowding them.

## 11. Point at one place in your own token structure that you would build differently if you started again. Say what you would do instead and what it would cost.
ANS- The place I’d build differently is theming. I defined one set of colour roles for a light surface and never tested a dark theme, even though I generated tonal palettes meant to support both. I’d build the dark mapping from the start: the same roles, pointed at different tones. The reason it matters is that contrast doesn’t carry over. My primary, 
#C2410C, measures about [5.2:1] against white, but against a near-black surface of 
#1A1A1A I calculate only about 3.4:1, which passes for large text and UI shapes but fails 4.5:1 for normal text. So in dark mode primary would need a lighter tone, and every role pair has to be re-measured. My shadows are built from the primary colour, and they are hard to see on a dark surface, so they would need rethinking too. The cost is time: re-measuring every pair, adjusting tones, and testing each screen again. The risk of leaving it untested is that I would find the failures only after a client reports unreadable text.


## 12. Wrong-answer analysis. A candidate says: "I set up design tokens by exporting the hex values from Figma into a CSS file, so every colour in the codebase comes from one place. That makes it a single source of truth." This sounds correct and is not. Say precisely what is missing and what will go wrong in month four.

ANS- The candidate has one file of values, not a single source of truth. First, hex values are primitives. Nothing says which hex is the button, the text or the background, so components bind to raw values instead of roles like primary and on-primary. Second, nothing enforces that the file is the only place colours come from. Anyone can paste a hex into a component, and the claim “every colour comes from one place” stays true only until they do. I tested this on a branch: I hardcoded one element,the tagline, then changed the brand colour at the source. Everything that referenced the palette changed, and the tagline stayed orange. 
Third, an export is a copy. Once Figma changes, the CSS file is stale unless someone re-exports, and my first export silently left out my colours. In month four, the brand colour changes in Figma, a few screens don’t follow, nobody knows which hexes are intentional, and a dark theme can’t be added because the values carry no meaning. The fix is a role layer, a repeatable export, and a search for raw hex values in components.
